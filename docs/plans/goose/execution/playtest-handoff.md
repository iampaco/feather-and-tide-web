# 斑头雁试玩执行单

版本为 Web 0.1.0、`goose-p0-7`，巡航雁资产 `ANM-001 v002`，实验场 `flight-1`，短规则航线 `rules-2`。关卡 schema、检查点与运行记录格式均为 v1。记录每次实测的生产包文件名。设备测试与首次玩家样本待实测。参照 [Q01–Q04](06-playtest-and-release.md) 填写结果。

## 运行

1. 在项目根目录运行 `npm ci`、`npm run check`。
2. 运行 `npm run preview -- --host 0.0.0.0`。保持手机、平板和服务器在同一局域网。各设备在 Safari 打开终端打印的 Network 地址并横置。
3. 记录机型、系统、浏览器、横屏、安全区、版本、画质、网络、样本、路线与模式。新玩家首次只收到目标“带全队抵达”。在第一次尝试结束后再测试具体操作。

如使用试玩归档，解压后在 `index.html` 所在目录运行 `python3 -m http.server 4173 --bind 0.0.0.0`。手机和平板用 Safari 打开同一局域网内的主机 IP 和端口 4173。

### 桌面宽幅鼠标环绕

先用经典视角飞过同一段，再开启「设置 → 镜头 → 宽幅鼠标环绕」。在 S2 从低角度观察身边的雁，再拉到高角度判断岔路。在 S3 回望接应圈，在 S4 边巡航边回望，在 S5 从观景廊旁拉低视角，在 S6 保持宽幅构图进入落脚。记录是否看清领队和通路、遮挡时镜头是否抬高和恢复、是否有意外转向及复位次数。诊断中的 `camera.pitch` 为实际俯角，`camera.requestedPitch` 为手势请求角度。

在真实 iPhone 和 iPad 横屏用单指拖镜检查经典俯角，同时保持另一手移动，再用同一手从观察区拖过结阵键。记录实际机型、系统、浏览器及首次试玩结果。

Q04 中断复测可在 S3 救援开始后同时保持移动与结阵，再转竖屏并等待两秒，横置后先核对剩余时间，点击继续后再试两个触区。另在 S6 刚出现 12/12 时转竖屏并等待四秒，再横置继续，检查演出从暂停处恢复。真实切后台及系统打断分别记录，转屏测试也记录方向锁定设置。

### 首航体验记录

邀请 5–8 位首次玩家，用真实 iPhone 或 iPad Safari 横屏飞行。开场只给目标「带全队抵达」，首航结束后再演示按键或指定分支。五人样本以至少四人能独立完成、说出两路差异和理解救援为参考。

| 机型与构建 | 主动滑翔 / 解阵 / 转镜 | 分路与理由 | 首次发现 / 接回队尾 | S5 改变飞法与理由 | 哪段觉得空或忙 | S5 失败后是否愿重试 |
| ---------- | ---------------------- | ---------- | ------------------- | ----------------- | -------------- | ------------------- |
|            |                        |            |                     |                   |                |                     |

首航后交换 A/B 顺序复测双手操作，再分别体验长湖浅滩、风场浅湾和逆风补给。记录玩家是否知道预警指向何处、补给是否需要等雁群跟上、为何落脚前出现等待。只有拿到真机和新手记录，再决定发布、默认映射和第二检查点。

失败复测从 A 选择山口。分别留出一次 40 秒接应超时和一次长距离加速后在安全水域外耗尽能量。失败前主动转镜，从检查点 A 重试，核对 12 雁、满能量、默认镜头与岔路，再改选长湖。诊断模式下，`#game` 的 `data-retry` 在点击重试时记录模拟继续前的只读恢复状态。

S4 实机复测沿外围水道和保护湿地通过，分别在接近风场前保持满阵和提前解阵。记录玩家何时认出出口、队尾是否跟上、是否收到扫掠反馈及是否获得补给。用 `FEATHER_REPLAY_DIR=/tmp/feather-s4 npm test` 生成四条固定步长参考航迹和 `s4-outer-water.json`，可核对标准、低档渲染轮廓与碰撞数据。

### Q01 镜头 A/B 记录

1. 完成首次自由尝试后，从标题进入飞行实验场，保持默认灵敏度和同一画质。各轮重新进入，从同一起点以摇杆向上朝直线航标巡航。

## 自动化复现

```sh
npm run check
npm run test:e2e
npm run test:e2e -- --grep 'paired A/B'
FEATHER_REPLAY_DIR=/tmp/feather-replays npm test
```

本机安装完整 Chromium 后，可以通过 `FEATHER_CHROMIUM_CHANNEL=chromium npm run test:e2e -- --project=chromium --workers=1` 使用完整浏览器的无头模式。默认仍沿用 Playwright 自带的测试启动方式。

运行以下命令保存生产入口的浏览器截图、帧时、落脚和刷新结果。试玩脚本会在本机分配预览端口。要测试已经运行的预览，可用 `FEATHER_PLAYTEST_URL` 指定地址。标准和低档复测可在同一设备分别执行。

```sh
node tools/browser-playtest.mjs /tmp/feather-browser mountain
node tools/browser-playtest.mjs /tmp/feather-browser lake webkit --low --roam
node tools/browser-playtest.mjs /tmp/feather-browser mountain webkit --s4-orbit
node tools/browser-playtest.mjs /tmp/feather-browser lake webkit --silent --s3-lookback --s4-orbit
node tools/browser-playtest.mjs /tmp/feather-browser lake webkit --audio
node tools/browser-playtest.mjs /tmp/feather-browser lake webkit --silent
```

回放 gzip JSON 使用 60 Hz，每条输入存为 `[x, z, ability]`。坐标是世界 XZ，能力位为 0 或 1。记录包含关卡版本、起始快照、按 tick 的事件和结束状态。失败夹具另保存重试状态。

浏览器脚本使用合成 Pointer Events 驱动正常输入路径。`--s3-lookback` 在河谷从默认构图转向队尾，记录接应提示。`--s4-orbit` 以 B 映射保持已按下的左手基准，在 S4 依次采集低俯仰左偏航和高俯仰右偏航画面，检查外围提示和警告是否重叠。对准安全航道时显示出口，接近危险时升级警告。真实触屏、首次玩家、A/B 手感、实机音画和性能门槛由实际操作者记录。P0 的实机和音画验收是 Y01–Y06 的前置条件。

`paired A/B` 在 `test-results/` 输出相同转镜序列的分段航向、位置和两张截图。用例在 Chromium 先 A 后 B，在 WebKit 先 B 后 A。仿真验收用固定的浏览器时钟推进每次手势，实机按上面的任务计时。

`--silent` 关闭游玩配乐。旅程脚本从同帧诊断和 HUD 记录圈外提示、领队转到目标方向 30° 内、首次满足接应条件和归队时的 tick。圈内超速使用浏览器定向用例验证。脚本立即回应提示，首次玩家的发现和决策用时单独记录。WebKit 原生媒体控件诊断单列，页面错误、资源失败和着色器错误继续使回放验证失败。

`--audio` 从浏览器直接录制游玩配乐，保留起飞前 1.5 秒的静默和完整落脚乐句。录制包含场景截图及对应时间，用于核对山口与湖路、接应同伴、保护湿地和落脚时的配乐衔接。录音仍需结合实际装置与操作体验复核。

### Q04 贴图版冷启动对照

用同一静态服务器分别托管 `ANM-001 v001` 的归档和当前 `v002` 构建，例如分别在两个解压目录运行本地 `python3 -m http.server 4174 --bind 127.0.0.1` 和 `python3 -m http.server 4175 --bind 127.0.0.1`。运行以下命令保存资源体积、冷启动时长和两个浏览器的 S0 图。

```sh
node tools/browser-startup.mjs /tmp/feather-startup http://127.0.0.1:4174/ http://127.0.0.1:4175/
```

两版均用新 Chromium 上下文与关闭缓存，每种条件各三轮。脚本交替顺序，在无额外限速的回环连接和 5 Mbit/s、120 ms 延迟的限速配置下，从导航开始量到菜单可用和首次移动。首屏载荷按 Resource Timing 的编码正文大小求和。iPhone 与 iPad 的 Safari 网络和内存另行实测。
